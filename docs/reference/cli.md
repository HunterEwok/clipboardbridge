# Command reference

Every command of `cbb`, on a full member (Linux, macOS, Windows) and on the lite member, with
their flags and environment variables. `cbb help` prints the short form of the one installed;
`cbb version` says which it is.
Commands other than `service`, `agent`, `version` and `help` talk to the running
service. `copy`, `paste`, `config`, `status` and `agent` use the control socket, which members of the
`cbb` group (`_cbb` on macOS) reach without `sudo`. Every command
that changes the group or this device's place in it (`new`, `pair`, `invite`, `remove`,
`rename`, `admin`, `takeover`, `recovery`, `handover`, `upgrade`, `freeze`, `unfreeze`,
`global on|off|hub|hubs|...`, and on the lite member `global on|off`) uses the admin socket, which
only root reaches: run it with `sudo`, on Windows from a terminal opened as administrator.

## cbb

| Command | What it does |
|---|---|
| `cbb copy [-secret]` | Sends standard input to the group, and to this device's own clipboard. `-secret` sends it as a secret: kept only in memory and gone 60 seconds after the copy. |
| `cbb paste [-terminal [-lines] [-secret]]` | Prints this device's clipboard text; in the sync modes `own` and `send`, which keep the group's copies out of the clipboard, the group's latest text. `-terminal` makes it safe to paste into a terminal, as tmux's paste key does: it drops the control characters (C0 but tab and line feed, DEL, C1), keeps only the first line unless `-lines`, leaves out the last line feed, and refuses a secret unless `-secret`. |
| `cbb copy [-text TEXT] FILE...` | Sends files and folders to the group as one copy (images and files, up to this device's `max-copy`): folders with their tree, links and special files left out, names made safe for every system (`notes.` becomes `notes._`). `-text` is the plain text that goes with it, for the devices that take only text. `cbb copy -type png\|jpeg\|html FILE` sends one file as clipboard data of that type instead, such as a screenshot. `cbb` reads the files as the user who runs it. |
| `cbb paste -o DIR` | Saves the clipboard's images or files in the folder `DIR` and prints what it wrote: files and folders by their names, an image as `image.png` or `image.jpg`, HTML as `clipboard.html`. It waits while the copy is still arriving, never replaces a file and makes nothing executable; in mode `own` it saves the group's copy. |
| `cbb paste -on DEVICE [-type] [-enter] [-secret] < text` | On an admin: remote paste, puts the text, or this device's clipboard text when standard input is a terminal, into the focused app or tmux pane on `DEVICE`, named by its name or ID, where its user turned remote paste on. `-type` types it key by key instead (at most 4 KiB), `-enter` presses Enter after it where the user allowed that, `-secret` sends it as a secret: not logged, and the clipboard there is cleared after. |
| `cbb paste-receive [on [-enter] [-console] [-no-lock-check] \| off [-on DEVICE \| -all]]` | Shows remote paste here, or turns it on or off; setting it needs `sudo` on Linux and macOS, administrator on Windows. On, the group's admins may paste into this device; `-enter` lets a paste press Enter, `-console` lets it reach the Linux text console and root's tmux. On Linux and FreeBSD a paste goes in only where logind says the session is not locked; `-no-lock-check` lets it go in also where nothing says, as without logind, and a running screen locker still stops it. An admin turns it off on another device with `-on DEVICE`, or on every device with `-all`. |
| `cbb remote [add [-appletv \| -roku -consent] [-name NAME] ADDRESS \| code CODE \| cancel \| remove TV \| pastes TV on\|off \| type [-tv TV] [TEXT]]` | Makes this computer the remote of a TV on the home network, with `sudo`. `add` pairs with an Android TV or a Google TV at ADDRESS (its address or name; ports 6467 and 6466): the TV shows a code, which `code` takes within two minutes, and `cancel` ends the pairing. `add -appletv` pairs with an Apple TV (the Companion port, 49153 unless ADDRESS names another): it shows a four-digit PIN for `code`, and it pairs only while its Settings, AirPlay and HomeKit, Allow Access is "Everyone on the Same Network". `add -roku -consent` takes a Roku (port 8060), whose External Control Protocol is plain HTTP: the text crosses the home network unencrypted, and the Roku needs "Control by mobile apps" set to Enabled or Permissive (Settings, System, Advanced system settings). `-name` names the TV here; by default it is the name the TV gives. `type` types TEXT, or standard input, into the field open on the TV, Enter for each line break (an Apple TV takes the line break into the text); `-tv` names the TV when there are several. `pastes TV on` sends the group's remote pastes to that TV instead of to this computer's screen (one TV at a time), where a line break needs `paste-receive on -enter`. `remove` forgets a TV. With no argument it lists the TVs. An address outside the home network is refused. |
| `cbb keyboard [on [-layout us\|ru] [-rate N] [-pastes] \| off \| pair \| type [TEXT]]` | Linux: makes this computer a Bluetooth LE keyboard for a TV, a tablet, a console or a computer near it, which needs nothing installed; with `sudo`. `on` registers it with BlueZ (5.50 or later, an adapter with Bluetooth 4.0 or later); `-layout` is the layout active on that device (`us` by default, or `ru`), `-rate` the characters a second (5 to 60, 20 by default), and `-pastes` sends the group's remote pastes there instead of to this computer's screen, where a line break needs `paste-receive on -enter`. `pair` makes it discoverable for two minutes, so that the device adds it in its Bluetooth settings without a code. `type` types TEXT, or standard input, on the connected device (at most 4096 characters), and refuses a text with characters the layout has no key for, naming them. With no argument it shows how the keyboard stands. macOS and Windows let no program be one. |
| `cbb config [max-copy\|max-copy-away SIZE]` | Shows or sets the largest copy of images and files this device sends or fetches: `max-copy` at home (100MiB by default, 1MiB to 1GiB) and `max-copy-away` from a member through the group's tunnel (25MiB, at most `max-copy`). A copy over the limit is not fetched, and `cbb status` says so. Sizes take KiB, MiB and GiB (MB and GB mean the same). |
| `cbb mode [own\|shared\|receive\|send]` | Shows or sets this device's sync mode, what moves between its clipboard and the group; set it with `sudo` on Linux and macOS, as administrator on Windows. `own`, a new device's mode, keeps the clipboard to itself: copies here stay here, the group's do not come, and `cbb paste` prints the group's text instead. `shared` sends copies to the group and takes the group's; `receive` only takes them, `send` only sends. `cbb copy` and the phones send to the group in every mode. |
| `cbb mode -on DEVICE own\|shared\|receive\|send` | On an admin: sets the sync mode of another device of the group (its name or device ID) with a signed command, which the device takes only while it is connected to this one; run it with `sudo` or as administrator. Phones and the lite member take it too. |
| `cbb mute [-for DURATION]` | Keeps the group's copies out of this device's clipboard for `DURATION` (up to `720h`) or until `cbb unmute`; this device's own copies still go out. It needs no `sudo`: any user of the `cbb` group (on Windows, of the computer) may switch it. The apps' first screen has the same switch. |
| `cbb mute -on DEVICE [-for DURATION]` | On an admin: mutes a device of the group (its name or device ID, this device too) with a signed command: its copies, `cbb copy` among them, do not reach the group until then or until an admin's `cbb unmute -on DEVICE`. The last admin's command counts; the muted device's own user ends it only where it is itself an admin or the root. |
| `cbb unmute [-on DEVICE]` | Takes the group's copies here again, or, on an admin, ends a device's mute. |
| `cbb incoming [DURATION]` | Shows or sets how long a copy from another device stays live, the group's setting for every device: within it the copy goes into the clipboard of each device whose mode takes the group's copies, after it the copy is gone. One minute by default, from `5s` to `1h` (for example `30s`, `2m`); setting it signs a record, on the root or any admin, with `sudo` or as administrator. |
| `cbb action` | Lists this device's quick actions, the presets `lock`, `sleep`, `reboot`, `shutdown`, `cancel-shutdown`, `restart` and `keyboard-layout` (the Bluetooth keyboard's next layout), and who may run each. Every one is off until this device's own user turns it on. |
| `cbb action enable NAME [-by root,phone,computer,watch] [-any-key] [-yes]`, `cbb action disable NAME` | Turns a quick action on or off here, with `sudo`. Enabling says what it lets the group's admins do and asks for `yes`; on Linux it writes the polkit rule that gives the service exactly the rights the actions that are on need (`/etc/polkit-1/rules.d/60-cbb.rules`), and disabling takes them back. `-by` limits it to those kinds of admins; `reboot` and `shutdown` take only admins whose keys are in hardware unless `-any-key`. A reboot or shutdown waits a minute, which `cancel-shutdown` stops. Linux runs them through logind, a Mac and Windows through the agent of the user signed in, so there they need someone signed in; a Mac locks when it asks for the password as soon as the display sleeps (System Settings, Lock Screen). |
| `cbb action add NAME [-by root,phone,computer,watch] [-yes] -- PROGRAM [ARGS...]`, `cbb action remove NAME` | Adds an action of your own here, with `sudo` or as administrator, after saying what it allows: the agent of the user signed in runs PROGRAM, given by its full path, with exactly these arguments and no shell, and the sender gets only its exit status. It must end within 15 s; start longer work in the background. `disable` and `enable` turn it off and on, `remove` takes it away. |
| `cbb action -on DEVICE NAME` | On an admin: runs the action NAME on another device (its name or device ID) with a signed command, and says whether it ran or why not. |
| `cbb action off [-on DEVICE \| -all]` | Turns every quick action off here, or, on an admin, on another device or on every device of the group; only each device's own user turns them on again. |
| `cbb status` | This device, its sync mode, its group, sync away from home, and every device of the group: its system (Linux, Windows, macOS, iOS, Android), its version, marked `(old)` below the newest signed release the group passed around, its role (`full`, `lite`, `phone`, `watch`), whether it is the root or an admin, when it was last seen and whether its clock is off. It also warns when members at home could not connect to this computer and sync only because it dials them back, as when a firewall here drops the member port, and says when a newer signed release is out. |
| `cbb rename NAME NEW-NAME` | Gives a device of the group, by name or device ID, another name (1 to 64 characters): an admin signs a new device record with it, and every device and app shows it once it hears of it. Runs on an admin, which renames any device, itself and the root included; the phones' Devices list does the same. |
| `cbb remove NAME` | Removes a device, by name or device ID, with a signed record; the group stays. Runs on an admin: the computer that created the group (its root), a computer the root made an admin (`cbb admin`), or a computer the root phone made an admin. Only the root (or an admin phone) removes an admin: an admin computer's key sits in a file, so it removes ordinary devices only. The root is removed with `cbb takeover`; a root computer that an admin took the group over from while it was away (`cbb status` there says so) removes that admin, which undoes the takeover. In a phone's group, remove devices in the app (Devices). |
| `cbb freeze NAME` | Freezes the admin computer NAME, as one that was stolen, on any admin: from then on nothing it signs counts beyond the records it signed before, which stay, and the members refuse its connections. It cannot freeze the root or an admin phone. Once frozen, an admin signs nothing more; two admins that freeze each other before either hears of the other's freeze both stay frozen until the root decides. |
| `cbb unfreeze NAME` | On the group's root: ends every freeze of the admin computer NAME, which is an admin again. In a phone's group, use "Unfreeze" on the root phone or an admin phone; `cbb remove` on the root (or Remove on a phone) removes it for good. |
| `cbb resolve` | On the group's root: voids both histories of every key that signed two (`cbb status` says which), as a stolen key or a computer brought back from an old backup would. The key goes on from the record before them, and the admin computer whose key it was signs again by itself what it signed since its last backup; what it did not sign stays void, so check the devices afterwards. |
| `cbb admin [-allow-file-key] NAME` | On the group's root: makes the computer NAME (a name or a device ID) an admin, which can then admit and remove devices. It must be connected. A computer whose keys sit in a file (a computer without a TPM or a Secure Enclave) becomes an admin only at the key level `files` (`cbb keys`) and with `-allow-file-key`: whoever copies that file can act as an admin until another admin removes it. In a phone's group, use "Make it an admin" on the root phone, which warns the same. |
| `cbb keys [proven\|hardware\|files]` | Shows the group's key level, or sets it on the group's root: which devices may be the group's root, an admin or a hub ([keys](../guide/keys.md#the-three-levels)). `proven` lets in only keys that attestation proves are in hardware, `hardware` (the default) keys in hardware by the device's own word too, and `files` keys in files too, each after a warning (`cbb admin -allow-file-key`). A group whose root computer keeps its key in a file starts at `files`, and its root cannot set a level its own key does not pass. Admins and hubs already below a new level stay, and the command names them, until you remove them. |
| `cbb install [options]` | Windows: installs the service, the agent and the firewall rules from the copy of `cbb` that winget unpacked, by running `packaging\windows\install.ps1` beside it in an administrator terminal; the options are the installer's (`-Express`, `-Port N`, `-HomeCgnat on`). Run it again after `winget upgrade`. |
| `cbb takeover NAME` | On an admin, when the root computer NAME is lost: this computer becomes the group's root and NAME is removed. The devices stay in the group. In a phone's group an admin phone takes over instead. |
| `cbb takeover -delay DURATION` | On the group's root: how long a takeover claim waits on each member before it holds, from 0s to 168h (72h by default), such as `cbb takeover -delay 24h`. |
| `cbb recovery` | When every phone with the group is lost: on any computer of the group, reads the recovery key from the sheet the root phone printed (typed in groups of four, or the text of its QR code) on the standard input, never the command line, and claims the group with it. After the group's wait (72 hours unless the root set another), unless the root phone cancels the claim, this computer is the group's root; the devices stay. The computer does not keep the key. `cbb recovery -yubikey` takes the recovery key on a YubiKey instead: it reads the YubiKey's PIN, finds the slot whose certificate is the key's admin CA, and the YubiKey signs the claim (with a touch when the root phone set one); the key never leaves it. On Linux and FreeBSD it needs `pcscd`. |
| `cbb handover NAME` | On the group's root: lets the admin NAME take the group over at once, without the wait, as a phone that joined a computer's group after `cbb recovery` (docs/protocol.md, section 10, "Handing the group over"). |
| `cbb global hubs NAME...` | Sets the group's main hubs for sync over the internet, by name or device ID, 1 to 16 computers and phones in the order they serve: they serve before the other hubs, which follow in the order the records give (docs/protocol.md, section 11, "Several hubs"). Runs on the group's root or on an admin that may be a hub; the root's table beats an admin's. |
| `cbb leave [-yes]` | Leaves the group, after a question that `-yes` answers: deletes this device's keys and the group's files here, keeps the program and its settings, turns remote paste and the quick actions off, and restarts the service in no group, so that `cbb pair` joins this group or another one. The group's root leaves only when it is alone; otherwise `cbb handover` first. For a device the group removed, or whose group file is damaged. The group lists the device until an admin removes it. |
| `cbb new` | Creates a group with this computer as its root: it holds the group's root key, admits devices and makes admins. A computer in a group already keeps it. |
| `cbb pair` | Does what this computer's place calls for. In a group, on the root or an admin: admits a new computer, showing a six-digit code to type there, and waits. In no group: joins one, showing a QR code for the phone app and taking the code of `cbb pair` on the group's root or an admin, typed meanwhile. On a member that is neither, it names the devices that admit. |
| `cbb pair -admin` | On the group's root: admits a phone with the app as an admin, showing first what an admin may do (add, remove and renew devices, freeze other admins, choose the hub, take the group over after the takeover delay), then a six-digit code to type in the app ("My group was made on a computer"). A plain `cbb pair` and an invitation refuse a phone that asks to be an admin. |
| `cbb pair -qr [-admin]` | On the group's root or an admin: admits a device that shows a QR code and waits for the group to dial it, such as a phone with the app on Aurora OS. It reads the code's text (`cbb://join?...`) from the terminal or standard input, never from the command line, dials the addresses it names on the home network only, and checks the device's certificate against the fingerprint in it. With `-admin`, on the root only, a phone that asks to be an admin becomes one, as with `cbb pair -admin`; without it such a phone is refused. The Mac app and the tray app do the same from "Add a device", with the code's text or a picture of it. |
| `cbb pair -code [ADDRESS]` | Joins with the code from `cbb pair` on the group's root or an admin, read from the terminal or standard input (never from the command line, where other users could read it). Without an address it finds that computer on the home network; with one (`host:port`) it dials it, for example through an SSH tunnel or your own VPN (see [Without the app](../guide/without-app.md#joining-from-another-network)). |
| `cbb pair -app FILE` | For the desktop apps, which run it as the administrator: in no group, joins by the phone's QR code as `cbb pair` does, but writes the code into FILE as one line of JSON (`qr`, the code's text; `expires`, the seconds the wait lasts; `port`, the member port the phone dials) instead of drawing it, and stops when FILE is removed. FILE must exist and be a regular file: cbb writes over it and never makes one. |
| `cbb pair -invite FILE` | Joins from afar with an invitation file from `cbb invite`, through the hub's guest tunnel. It runs with `sudo` on Linux and as administrator on Windows, as `cbb global on` does: the service may reach the hub's addresses from the invitation, and a failed join takes them away again. Both sides show the new device's key fingerprint; the hub admits it once its admin types `yes`. |
| `cbb invite [-for DURATION] [-o FILE]` | Runs on the group's hub, with sync away from home on: writes an invitation for a device away from home (default `cbb.cbbinvite`, valid for 1h, at most 24h) and waits to confirm it. The file is a secret until it is used; copy it through a channel you trust. |
| `cbb global` | Shows sync away from home on this device: on or off, the hub, the tunnel, and what went wrong. |
| `cbb global on` | Turns sync away from home on here, after a warning about where the keys are kept. On Linux it runs with `sudo`, on Windows in a terminal opened as administrator: the service may reach only the home network, and it lets it reach the group's own servers (hub, forwarder, relay) as well, and nothing else on the internet: a systemd drop-in with their addresses on Linux (the service restarts), the outbound rule `cbb-home-only` of Windows Firewall without them; on a Mac only the service's own limit follows, and `sudo` is not needed. A client waits a few seconds for its hub's offer, which names the hub's addresses. |
| `cbb global allow` | Lets the service reach the group's servers as it knows them now, run as `cbb global on` is: after the hub's addresses changed or first became known, when `cbb global` or `cbb status` says the system's limit lags behind. With sync away from home off or in no group it takes back what the limit allowed. The installers run it after an update, so a limit an earlier version left (on Linux, a drop-in that allowed every address) follows the current state. |
| `cbb global off [-yes]` | Turns it off and forgets the tunnel keys. New keys reach the hub only on the home network, so on a device that reaches its hub only through the tunnel it asks first (`-yes` does not): such a device syncs with its group again only once it is at home, even after `cbb global on`. Run as `cbb global on` is, it also takes the group's servers out of the limit, so the service may again reach only the home network. |
| `cbb global off -on DEVICE` | On an admin computer: turns sync away from home off on the device DEVICE, which forgets its tunnel keys as above. Turning it on stays that device's own decision. A watch may send it too. |
| `cbb global hub [-away-on] [-keep] [-port N] [-firewall ask\|yes\|no] [-obfuscate] [-forwarder ADDRESS:PORT -forwarder-key KEY] [-vless] [ADDRESS:PORT...]` | The forwarder may be given by name (`cbb.tools:8764`); the command looks the name up once and the hub keeps the address. Makes this device the group's hub, reached from the internet at these addresses, through a forwarder, or both; `-port` sets the UDP port the tunnel listens on. With `-forwarder` the hub registers with that forwarder, whose key `-forwarder-key` pins, and its clients try it after the hub's own addresses. `-obfuscate` makes the tunnel speak AmneziaWG, for networks that block WireGuard: the hub makes the group's settings once and keeps them while `-obfuscate` stays, and its clients get them at home with its offer; with a forwarder, the hub gives it the settings. `-vless` turns AmneziaWG on as well and has the clients try it over UDP first and then reach the forwarder inside VLESS, which looks like HTTPS to a website, for networks that block WireGuard and AmneziaWG alike; they never send plain WireGuard; the forwarder must run with `-vless-xhttp` or `-vless-site`, and tells the hub which. `-keep`, on a hub, keeps its own addresses, port and forwarder where the command gives none, so that `cbb global hub -keep -obfuscate` (as the apps' switches run it) changes only how the tunnel hides. A hub reached at its own address lists the firewall rule its UDP port needs (from any address, since its clients are on the internet) and asks before it adds it, as the installers do; `-firewall yes` adds it without asking, `-firewall no` prints the commands. cbb closes the port again when this device stops being a hub reached at its own address (another port, only a forwarder, `cbb global off`). A router in front of it must forward the port too. The hub need not stay on: while it is off nothing syncs away from home, and at home the devices sync without it. Where sync away from home is off, `-away-on` turns it on first, after the warning of `cbb global on`, in the same step; the Mac app and the tray app run it so for "Make it a hub" on this computer, after the same question. |
| `cbb global hub off [-on DEVICE] [-yes]` | Stops being one of the group's hubs, or, on an admin computer with `-on`, makes the hub DEVICE stop with a signed `hub` command. The clients connected to it get the next hub's offer and go there without coming home; this device stays a client with sync away from home on, and the devices that keep its offer forget it. When the group has no other hub it refuses, since the devices away from home would stop syncing, unless `-yes` agrees to that. The Mac app and the tray app offer it as "Stop being the hub" on a hub's page. |
| `cbb global hub -on DEVICE [-forward-only] [-forwarder ADDRESS:PORT -forwarder-key KEY] [ADDRESS:PORT...]` | On an admin computer: makes the admin computer DEVICE (its name or device ID) a hub of the group as well, with a signed `hub` command, reached through the forwarder (without addresses, the project's at `cbb.tools`) or at the addresses given; this device stays what it is. DEVICE must have sync away from home on, which only its own user turns on. A hub hands it its clients, and a device with sync away from home on hands itself and keeps the new hub's offer. With `-forward-only`, DEVICE may be any computer that is no admin: this device first signs it a record that makes it a hub that only passes the copies on, sealed, so that it reads none, makes none and takes no paste or action; no key level applies to it. The phone apps, the Mac app and the tray app offer the same as "Make it a hub". |
| `cbb global move DEVICE [-forwarder ADDRESS:PORT -forwarder-key KEY] [ADDRESS:PORT...]` | On the hub, a computer, with `sudo` (on Windows as administrator): hands the hub's role to the admin computer DEVICE (its name or device ID), which must have sync away from home on and no relay. The new hub keeps this hub's forwarder, or the one `-forwarder` names, and the addresses given; every client follows without coming home, and this computer becomes the new hub's client. A lite member or a container cannot take it. The phone apps offer the same as "Move the hub to a computer". |
| `cbb global relay default\|ADDRESS:PORT -key KEY [-yes]` | `default` is the project's open relay at `cbb.tools:8765`, whose address and key cbb knows, and takes no `-key`; the service takes its keys and address from the project's signed lists at each start and when it fails to register there, so a new key or address reaches it without a release. The relay may be given by name, looked up once. For a group without a hub: this device meets the group's other devices away from home at the blind relay at that address, whose key `-key` pins. It first says what the relay learns (which devices are online and from where, which talk, when and how much) and asks you to type yes; `-yes` agrees without asking, for scripts. It registers there with its member certificate, and the relay joins its member connections to the others' end to end. It replaces the hub and the hub's offer on this device. |
| `cbb global entries [export [-qr] \| import STRING]` | Shows the signed entry points this device holds: the project's forwarders and their ways in over VLESS, which a hub of the project's forwarder registers through when nothing else gets through (docs/protocol.md, section 16, "Entry points"). `cbb update` fetches them and the group passes them on; `export` gives them as a `cbb-entries:` string, or with `-qr` a QR code, for a device that reaches neither, and `import` takes such a string, which the service checks under the project's keys as it checks a download. |
| `cbb forward [-listen ADDRESS:PORT] [-key FILE] [-state FILE] [-show-key] [-vless-xhttp NAME [-vless-path PATH] [-vless-port N] \| -vless-site NAME] [-vless-listen ADDRESS:PORT] [-vless-mirror ADDRESS:PORT]` | Runs a forwarder on a server with a public address, for hubs that clients cannot reach directly, for example behind carrier-grade NAT (default port 8764, UDP and TCP). It holds no keys of any group; it keeps only `-state` (default `forward-state.json` next to the key; `none` keeps it in memory only): under a keyed hash of each period's tag, the version of its newest server credential and a hash of its period key, so that an older credential or another period key is refused, also after a restart. `-records` names the folder of the files per group that versions before 0.6 kept; they are deleted. Its own key is made in `-key` on the first run (default `forwarder.pem` in systemd's state directory, or in the service's state directory) and printed at start, or alone with `-show-key`. With `-vless-site`, it also takes VLESS with REALITY on TCP `-vless-listen` (default `:443`) for the clients of hubs that ask for it, borrowing the TLS of that well-known site (such as `www.example.com`), whose own answers whoever is not a client gets; its REALITY key is kept in the same key file. With `-vless-xhttp` instead, it takes VLESS over XHTTP behind the web server of its own site (such as `cbb.tools`), which ends the TLS with the site's certificate on TCP `-vless-port` (default 443) at the forwarder's address and passes the path `-vless-path` as plain HTTP to `-vless-listen` (default `127.0.0.1:3276`); without `-vless-path` a random path is made once and kept in the key file, and the forwarder prints it at start for the web server's configuration ([self-hosting](../admin/self-hosting.md)). With VLESS, `-vless-mirror` names the mirror of the releases on the same server (such as `127.0.0.1:443`, the web server that serves `dl.cbb.tools`), which the clients of registered hubs reach over VLESS, and nothing else, for updates on networks that block the mirror. |
| `cbb relay -group TAG[,TAG...] \| -open [-listen ADDRESS:PORT] [-key FILE] [-show-key]` | Runs a blind relay on a server you run, for groups that have no computer to be the hub (default port 8764, UDP and TCP). It serves only the groups whose tags `-group` lists (`cbb status` shows a group's tag), or with `-open` every group that registers, within limits per group and per network, holds none of their keys, reads nothing of the clipboard, and writes nothing about them; it sees which devices of a group talk, when and how much. Its keys are made in `-key` on the first run (default `relay.pem` in systemd's state directory, or in the service's state directory), and the key to give `cbb global relay -key` is printed at start, or alone with `-show-key`. |
| `cbb update [-check \| -to VERSION]` (with sudo) | Installs the newest signed release of the `stable` channel on a computer installed with `get.sh`, `get.ps1` or a release archive, with the release's own installer, and puts the previous programs back when the service does not report the new version within a minute ([install guide](../guide/install.md#updating)). `-check` only says whether there is a newer one, and works without sudo. `-to VERSION` installs that release, for one whose `min_from` is above this device's version. A copy from Homebrew, winget, Docker or a package prints the command that updates it instead. Away from home over VLESS, it reaches `dl.cbb.tools` through the hub's forwarder; when no update server answers, it takes the signed release the group passed to the service. The release it checked goes to the service, which passes it to the group; the archive comes from the group's members when one has it, and the one installed goes to the service, which serves it to them. |
| `cbb update -auto [on\|off]` (with sudo) | Shows (`on`, `off` or `unset`), or turns on or off, updating once a day by itself: a systemd timer, a launchd job, a scheduled task as SYSTEM, or cron on OpenWrt and FreeBSD, which runs `cbb update -timer`. |
| `cbb update -mirror [URL\|default]` (with sudo) | Shows, or sets, where updates come from: GitHub and then `dl.cbb.tools` by default, or another `https://` mirror with the same layout as `dl.cbb.tools`. |
| `cbb version` | Prints the version and the platform. |

### Rarely needed

The system starts `service` and `agent`; they are run by hand only to look into a problem, such as to
see the agent's log in a terminal.

| Command | What it does |
|---|---|
| `cbb network` (with sudo) | Takes the networks this computer is on now as networks where its group is. A computer publishes itself and takes connections only on those (design.md, "Known networks"); it learns them by itself when it creates or joins the group, opens a pairing window or connects to a member there. Needed only at home after a new router, when every member keeps quiet; `cbb status` says "Quiet on" for such a network. |
| `cbb update -installed-by get\|brew\|winget\|docker\|package` | Records how this copy was installed; the installers run it. |
| `cbb service [-state DIR] [-socket PATH] [-user USER]` | Runs the service; started by systemd, launchd, rc.d, procd or the Windows service manager, not by hand. `-state` is the folder of its keys and state (the system's default, [devices](devices.md#files-and-logs)), `-socket` the control socket, and `-user` the user it runs as after it opened the mDNS sockets, when it starts as root (FreeBSD's rc script). |
| `cbb agent` | Links this desktop's clipboard to the service: the Mac's pasteboard, the Windows clipboard, or a Linux desktop's through Wayland or X11. It starts by itself at sign-in (`cbbw.exe agent` on Windows; on a Linux desktop the user unit `cbb-agent.service` where the desktop starts `graphical-session.target`, as GNOME and KDE Plasma do, else the autostart entry); run it by hand only to see its log. One runs in each session: a second exits. On Linux the installer starts the user unit again in each running session after an update, so there is no need to log out and in. |

## The lite member

On a small Linux device `cbb` is the lite member, with the same paths and service as a full
member (`/var/lib/cbb`, `cbb.service`) and the commands below; the
commands of a full member, such as `invite` or `remove`, answer that this is the lite member.
Global flags, before the command: `-state DIR` (default `/var/lib/cbb`, or
`CBB_STATE`), `-socket PATH` (default `/run/cbb/control.sock`, or `CBB_SOCKET`),
`-debug` (the details of errors). The commands that change its state, such as `pair`, run
as the service's user: `sudo -u cbb cbb pair`. Install and use are in
[member/README.md](../../member/README.md).

| Command | What it does |
|---|---|
| `cbb pair [-name NAME] [-port PORT] [-addr HOST[:PORT]]...` | Joins a group by QR code, scanned by the phone app. `-addr` names where the phone reaches this device, when the QR code would name the wrong addresses. |
| `cbb pair -code HOST:PORT` | Joins with the code from `cbb pair` on the group's root or an admin. |
| `cbb service [-name NAME] [-port PORT] [-peer HOST:PORT]... [-no-mdns] [-no-listen] [-tunnel-via HOST:PORT]` | Runs the service (systemd or procd), as `cbb service` does on a full member. `-peer` names a full member on the home network to dial, for networks without mDNS; `-no-mdns` turns mDNS off; `-no-listen` closes the member port, so the device only dials. |
| `cbb global [on\|off]` | Shows sync away from home, or turns it on (after the warning about keys in files, typing yes) or off here. Once on, the device meets the group's hub at home, keeps its offer, and away from home reaches it through the group's WireGuard tunnel; a hub that hides its tunnel (`-obfuscate`, `-vless`) keeps the lite member at home. |
| `cbb leave [-yes]` | Leaves the group, as on a full member: through the service, or by itself when the service does not run. |
| `cbb copy [-secret]` | Sends standard input to the group. |
| `cbb paste [-terminal [-lines] [-secret]]` | Prints this member's clipboard text, or the group's text in a sync mode that does not receive; `-terminal` as on a full member. |
| `cbb mode [own\|shared\|receive\|send]` | Shows or sets the sync mode, as on a full member; setting it needs `sudo`. A lite member that joins starts in own. |
| `cbb mute [-for DURATION]`, `cbb unmute` | Keeps the group's copies out of this device for a while, or takes them again, as on a full member. An admin's mute reaches the lite member as a command; it ends only by an admin. |
| `cbb status` | This device, its sync mode, its group, and every device of the group with its system, role and marks. |
| `cbb watch [-0]` | Prints each text the group sends here, one per line, or followed by a zero byte with `-0`. |
| `cbb action [enable NAME [-by root,phone,computer,watch] [-any-key] [-yes] \| disable NAME \| off]` | Shows the quick actions here, or turns one on or off, as on a full member, with `sudo`: `reboot` (a minute later; only for admins whose keys are in hardware unless `-any-key`), `cancel-shutdown` and `restart`. Enabling `reboot` writes the polkit rule that lets the service ask logind for it, so the device needs polkit. Any admin turns them off from afar. |
| `cbb paste-receive [on [-enter] [-console] [-no-lock-check] \| off]` | Shows remote paste here, or turns it on or off, as on a full member; setting it needs `sudo`. On, the group's admins may put a text into the tmux pane in use; `-console` lets it reach the active text console and root's tmux, `-enter` lets a paste press Enter, and `-no-lock-check` lets it reach a console whose session logind says nothing about being locked. Any admin turns it off from afar. |
| `cbb paste-helper tmux\|console` | The paste targets: tmux starts the one for tmux from cbb's `tmux.conf`, the `cbb-console` unit (`install.sh --console`) runs the one for the console. |
| `cbb next paste [-max BYTES]`, `next copy LEN CRC32`, `next pair [-name NAME] [-port PORT] [-addr HOST[:PORT]]...` | The same for the ZX Spectrum Next's `.cbb` dot command, in frames its Z80 reads; see [member/README.md](../../member/README.md#zx-spectrum-next). |
| `cbb update [-check] \| -auto [on\|off] \| -mirror [URL\|default]` (with sudo) | As on a full member, for the lite member's own archive on Linux and OpenWrt: the signed files checked, the download through the system's curl, wget or uclient-fetch, the archive's installer, and the previous program put back when the service does not report the new version within a minute. |
| `cbb version`, `cbb help` | The version and that this is the lite member; this help. |

## Installers

| Installer | Options |
|---|---|
| `get.sh` (Linux, OpenWrt, macOS and FreeBSD) | Downloads this system's archive, checks it against `SHA256SUMS` and runs its `install.sh`. `--express` adds the firewall rules without asking, `--no-firewall` adds none, `--port N` sets another member port, as for `install.sh`; on Linux also `--console`, `--uinput` and `--lite` for the lite member instead of the full one, and on OpenWrt `--lite` (on MIPS without sync away from home yet); `--no-pair` as for `install.sh`. `--rootless`, run without `sudo` on Linux, installs the full member, or with `--lite` the lite member, for the user who runs it (as `install.sh --rootless`). `--auto-update on\|off` answers whether it updates itself once a day (asked otherwise). With the one-line installer, put them after `sh -s --`. `CBB_VERSION=v1.2.3` installs that release. Running it again updates. |
| Linux `install.sh` (the same in the full and the lite member's archive) | Finds the firewall (ufw, firewalld, nftables, iptables), lists the rules Copy Beyond Borders needs and asks `Add these rules now? [y/N]`; the answer is kept in `/etc/cbb/firewall.answer` for later runs. `--express` adds them without asking and reports them, `--no-firewall` adds none and prints the commands that would; nftables and iptables always get the commands. `--port N` another member port (kept for later runs; `--port 8764` goes back), `--console` also starts tmux on the text console and the console helper for remote paste there (the `cbb-console` unit, in both archives). `--uinput` (the full member) adds the uinput helper, the `cbb-uinput` unit, which presses the keys of a remote paste on a desktop without another way (GNOME and KDE without the portal's dialog), and loads the `uinput` module at boot. `--auto-update on\|off` (the full member) answers `Update automatically? [y/N]`, which it asks otherwise and keeps (`cbb update -auto`). The lite member, once running in no group, starts pairing at the end (`cbb pair` as the user `cbb`) and shows its QR code, when the output is a terminal; `--no-pair` (or `CBB_PAIR=no`) skips it for a scripted install; a script that runs the installer with a terminal (`ssh -t` too) needs it, or it waits up to 5 minutes for a phone. Ctrl+C stops only the pairing. `--rootless`, run without `sudo`, runs `install-rootless.sh`: the full or the lite member for that user alone (D-79), in `~/.local/bin` with systemd user units, the state in `~/.local/state/cbb`, and no firewall rules, `--console` or `--uinput`; `--port N`, `--home-cgnat` and `--auto-update` work there too, and `sh ~/.local/share/cbb/uninstall.sh` removes it. |
| Linux `uninstall.sh` (`/usr/local/share/cbb/`) | removes the program, the service, the update timer and the firewall rules the installer added; `--purge` also deletes the keys in `/var/lib/cbb`. |
| OpenWrt `install.sh` (in the Linux archive's `packaging/openwrt`) | Installs `cbb` to `/usr/bin`, the user and group `cbb`, the procd script `/etc/init.d/cbb`, the settings `/etc/config/cbb` (port, zones, `wait_ntp`, `memlimit`; kept on a reinstall), the NTP hook and the list of files sysupgrade keeps. `--port N` sets the port in the settings, `--auto-update on\|off` as on Linux (from cron). The lite member starts pairing at the end as on Linux (`cbb pair -name router`), and `--no-pair` skips it. The firewall rules are the service's own procd data, which fw4 loads while it runs: the member port and mDNS from the listed zones other than `lan`, and the hub's UDP port from `wan` while this router is the hub. |
| OpenWrt `uninstall.sh` (`/usr/share/cbb/`) | stops the service, whose rules go with it, and removes what the installer added; `--purge` also deletes the keys in `/etc/cbb`. |
| FreeBSD `install.sh` | Installs `cbb`, the user and group `cbb`, the rc.d script (daemon(8)) and `cbb_enable="YES"` in rc.conf. Finds pf or ipfw and asks before it adds the rules: for pf in its own anchor, with three marked lines at the end of `/etc/pf.conf` that load it; for ipfw in rule set 17, added again at each start. `--port N`, `--home-cgnat`, `--auto-update`, `--express` and `--no-firewall` as on Linux (the update from cron); the settings are in `/usr/local/etc/cbb`. |
| FreeBSD `uninstall.sh` (`/usr/local/share/cbb/`) | removes the program, the rc.d script and its rc.conf line, and the firewall rules and pf.conf lines the installer added; `--purge` also deletes the keys in `/var/db/cbb`. |
| macOS `install.sh` (in the release archive's `packaging/macos`, or under `$(brew --prefix)/opt/cbb/share/cbb`) | `--port N` another member port (kept for later runs; `--port 8764` goes back), `--in-place` has the agent and `cbb` in PATH run the binary where it is (Homebrew) instead of copying it, while the service runs a root-owned copy under `/Library/Application Support/cbb/bin`; it asks before it lists the service in the application firewall, and `--express`, `--no-firewall` and `--auto-update` (not with `--in-place`: Homebrew updates it) work as on Linux. |
| macOS `uninstall.sh` (`/usr/local/share/cbb/`) | removes the service, the agent and the program; `--purge` also deletes the keys. Before `brew uninstall`. |
| Windows `get.ps1` and `install.ps1` | Lists the Windows Firewall rules Copy Beyond Borders needs and asks before it adds them; the answer is kept for later runs. `$env:CBB_PORT = "9000"` (or `-Port`) another port, `$env:CBB_FIREWALL = "express"` (or `-Express`) adds the rules without asking, `$env:CBB_FIREWALL = "no"` (or `-NoFirewall`) adds none and prints the commands, `$env:CBB_AUTO_UPDATE = "on"` or `"off"` (or `-AutoUpdate`) answers whether it updates itself once a day, from a scheduled task. The outbound rule that keeps the service at home is added either way. |
| Windows `uninstall.ps1` (`$env:ProgramFiles\cbb`), or Settings, Apps | removes the service, the agent, the program, the update task and the firewall rules; `-Purge` also deletes the keys and the `cbb` group. |
